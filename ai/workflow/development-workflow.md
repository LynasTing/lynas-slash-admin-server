# 开发工作流

## 实现方案评审

当用户提出具体实现方案时，编码前必须先评估，而不是直接照做：

- 确认方案是否真正满足需求，并检查与现有架构、接口契约、数据模型和兼容边界是否一致。
- 查阅适用的官方文档、项目依赖的最佳实践和成熟社区惯例，评估方案的可行性、维护成本、扩展性、性能与安全风险。
- 方案合理且可行时，说明关键取舍后再实施；不因“社区常见”而忽略项目实际约束。
- 方案存在明显缺陷、风险不可接受或有更合适的替代方案时，禁止直接实现。应明确结论、解释不合理之处及其后果，提出可行替代方案，并等待用户决定。
- 事实、约束或需求不足以判断时，必须说明未知项并先补充信息；不得把未经验证的假设当作结论。

1. 阅读 `agent.md`、相关规则和现有实现；确认需求、兼容边界及受影响模块。
2. 完成实现方案评审后，设计接口、错误处理、数据约束和事务边界，再实现最小完整改动。
3. 为新规则或缺陷补充合适层级的测试；不要用全量启动掩盖缺少单元测试的问题。
4. 按风险执行验证：文档改动检查链接和 Markdown；局部 Java 改动运行 `./mvnw validate` 与针对性测试；依赖、配置、跨模块或数据库改动再执行 `./mvnw test` 或构建验证。格式问题用 `./mvnw spotless:apply` 修复，不能手工猜格式。
5. 查看 `git diff` 与 `git diff --staged`，确认没有凭据、调试代码、无关格式化或生成物。
6. 使用 Conventional Commits 提交；钩子失败时修复根因，不用 `--no-verify` 绕过。
